# Automatic memory injection and extraction tracing

Memory injection emits `memory.inject`; queued extraction emits `memory.extract` through the existing `Strands.Agents` activity source. This increment extends the automatic search/add instrumentation described in `MEMORY_TELEMETRY.md`. It does not configure an exporter or add public manual memory tracing helpers.

Injection starts after the configured predicate or user-turn gate succeeds. Its activity is active around query derivation, retrieval, rendering, and ephemeral model-input projection. The nested `memory.search` activity therefore has the injection span as its parent in both memory telemetry profiles. Durable conversation history remains unchanged, and the existing trailing-block cache hint includes only a suffix actually appended to the final message.

The activity records `memory.max_entries`, `memory.injected`, and `memory.entry.count`. Predicate rejection or failure starts no memory activity. An empty query, no results, or a query error records false/zero; rendering failure also records `memory.inject.format_error=true`. The pinned tracers finish injection successfully even on these fail-open outcomes and caller cancellation. Caller cancellation still propagates with its exact supplied token, retaining a mismatched backend cancellation as the inner cause. A successful renderer sets injected/count before the existing empty-content and anchor guards: whitespace output can report successful rendering without an input projection. This flag follows the upstream renderer contract rather than claiming a durable message mutation.

Extraction records the store name, messages surviving the content filter, messages entirely removed by it, optional extractor type, and entries saved. The activity is active around extraction and backend writes in both profiles. A failed extraction ends as an error and omits the unknown entry count. Pending messages remain eligible for retry. A fully filtered batch records zero entries and advances its completed mark without backend I/O. Observational listener and diagnostic failures cannot turn confirmed writes into retries.

Each queued extraction is a root activity with an optional causal link. Built-in invocation/interval triggers capture that agent's recording invocation context synchronously when they enqueue work; the context remains usable as a link after the scheduling span ends or another batch delays execution. Custom triggers capture the actual sampled ambient activity at their firing boundary. Unrecorded agent contexts do not fall back to an unrelated ambient span. Explicit `FlushAsync` extraction starts an unlinked root, even when its caller has an ambient activity. Canceling a flush stops its wait and does not cancel already accepted extraction I/O.

The link contract is explicit native causality. It does not rely on an upstream comment's assumption that an invocation activity is still ambient when an after-invocation hook runs. No SDK trace receipt is inserted into caller invocation state, and no global hook ambient context is changed. The existing TypeScript/Python differences for raw search/add payloads and backend ambient activation remain as documented in `MEMORY_TELEMETRY.md`. Injection/extraction activities add no raw transcript events. The model extractor's specialized chat span and public manual helper APIs remain separate work.

The focused suite contains 23 contracts. Two scenarios were observed failing before implementation: injection span creation and linked extraction span creation. Nineteen conformance cases passed on their first run; two cancellation fixtures were corrected to test the established public cancelled-result and pre-model-hook boundaries, rather than counted as product fixes. The suite covers both profiles, delayed roots linked to ended runs, serial queue origins, explicit flush, cancellation, skipped/render-failed injection, failed-save retry, content filters, custom extraction, unrecorded spans, and failing listeners. Independent read-only review passed. Local `net48` execution uses installed .NET Framework 4.8.1 and is not a clean Framework 4.8 cloud claim.

The exact local gate passed 670 tests across six TRX files: 228 memory/telemetry regressions on each modern target, 53 portable contracts on each modern target, and 54 on each actual Framework x64/x86 host including its pointer assertion. It includes 138 executions of the 23 new contracts, with no failures, skips, or build warnings. Positive formatting probes covered all six source files and the test file, followed by clean verification. The tested source was the frozen `f343cb1` checkpoint plus the separately reviewed per-operation W3C prerequisite and this bounded increment. The initial Framework run's three empty-context/link failures are retained as evidence for that prerequisite; they were not corrected by changing process-wide activity settings in the tests.
