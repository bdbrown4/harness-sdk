# Live tool provider publication: Stage 1 review history

This document records the frozen intermediate Stage 1 review. The completed capability, background retention, MCP fan-out, and validation boundaries are described in [Live tool provider updates](LIVE_TOOL_PROVIDER_UPDATES.md). Status statements below describe that historical checkpoint.

This isolated checkpoint adds generic provider notifications and guarded native Agent publication. It is not a complete feature or an integration-ready capsule: MCP consumer fan-out and admitted background metadata retention remain Stage 2 prerequisites. Do not publish this checkpoint while those boundaries remain open.

`AgentOptions.EnableToolProviderUpdates` defaults to `false`. Existing providers still use `AddConsumerAsync`, one-time `LoadToolsAsync`, and attempted-all `RemoveConsumerAsync`. An opted-in provider implementing the additive `IToolProviderUpdates` capability supplies its initial full snapshot through `WatchToolsAsync` instead of a second load. The setup token governs establishment; the returned subscription owns later delivery until disposal or consumer removal. A missing initial snapshot, null lease, initial error or cancelled setup fails initialization and joins the available provisional lease before consumer removal.

Each observer belongs to one declaration and Agent. Updates copy membership, filter before reading `Spec`, capture detached metadata and compile validation before taking the lifecycle gate. A full replacement removes only its own registrations, preserves foreign order, and appends its new batch in source order. Foreign exact or configured normalized collisions reject the entire candidate. One capability reference cannot belong to two registration owners; same-owner snapshots can reuse their capability reference. The Agent preserves original rich/streaming/delegation interfaces and never adopts tool or provider ownership. Metadata and selected reference are frozen; arbitrary mutable implementation state inside a borrowed tool is not.

Active initialization, model invocation and continuations, direct calls, foreground human pauses, abort and classic reduction retain their accepted table. Updates coalesce to the newest valid prepared sequence. Pure release/admission pulses publish the pending batch when safe. Snapshot restoration publishes only after a successful validated commit clears its pause; failed or cancelled restoration retains the table. Application callbacks, provider disposal and logging run outside the table gate. Diagnostics carry physical activity accounting and cannot replace invocation or cleanup failures.

Terminal `OnError` and `OnCompleted` discard an unpublished pending refresh and retain exactly the last published table. A valid initial snapshot may complete before its lease returns; no initial snapshot still fails. Late or older-generation notifications cannot revive a closed source. Errors are observable through the existing borrowed SDK logger. There is no automatic reconnect.

Existing Agent admission still rejects external shutdown/disposal while initialization is active. Failed establishment itself joins admitted initial preparation and available lease cleanup before completing its failure. After initialization, external close joins admitted refresh preparation and available lease cleanup. New update cleanup is recorded once per subscription, preserves exact exception references, and does not self-attach or repeat a memoized close failure in the initialization journal. Existing provider removal cleanup behavior is unchanged.

A live callback cannot synchronously await its consuming Agent's own shutdown/disposal. Expired receipts normally cease to impose that guard; this does not detect every arbitrary self-wait through cached tasks or external application scheduling. Providers must cooperate with their own asynchronous lifecycle contract.

The pinned TypeScript Agent installs an MCP callback that removes old names then adds/replaces the refreshed batch (`src/agent/agent.ts:861-869`). Python's generic registry loads providers initially (`src/strands/tools/registry.py:130-142`); its MCP cache callback is a separate capability. Default-off native publication, full-batch owner collision rejection and safe-idle deferral are explicit native choices. Harness delegation catalogs and Bidi advertisements do not automatically become live through this Core option.

Current author evidence is focused net10 only: ten observed runtime RED cases were fixed, and the Stage 1 test group has 30 passing cases. Portable/API/regression acceptance and final independent runtime re-review are pending. The background scheduler can publish `Cancelled` before a body physically returns; Stage 2 must retain each admitted tool/spec/validator and use actual physical completion rather than terminal task status. No background safety or MCP live-publication claim is made by this checkpoint.
