# Model observation hooks

`HookRegistry.Register<T>` accepts the existing `IAgentStreamEvent` interface. `ModelStreamUpdateEvent` and `AgentResultEvent` can now be registered directly. Their positional constructors, deconstruction and record inheritance remain available. Agent-produced instances also expose the invoking `Agent` and the unchanged caller `InvocationState`; manually constructed model updates can remain unbound. Newly added context properties are excluded from the existing records' JSON payloads.

Unbound model updates share a read-only empty context, preserving value equality and matching hash codes for equivalent old-constructor instances. Bound model-update equality also includes the agent and invocation-context reference. The two new completed-event records serialize only their observation payloads, respecting the serializer's property naming policy; their agent and caller context are excluded. Those payloads cannot deserialize an invoking agent, so constructing a new bound observation requires the explicit public constructor.

`Register<HookEvent>` keeps its class-based matching rules. It includes lifecycle events and the new `ContentBlockEvent` / `ModelMessageEvent`, but not the existing model-update/result records, whose inheritance remains unchanged. Use `Register<IAgentStreamEvent>` to observe both categories. Existing lifecycle events are not dispatched a second time.

The observation boundaries follow the pinned TypeScript implementation:

- `ModelStreamUpdateEvent` is dispatched once, before that same instance is exposed by the model stream. Middleware can filter these observations. Old-constructor or foreign-context events emitted by model middleware are rebound to the current agent and original invocation state.
- `ContentBlockEvent` follows a valid raw content-stop update. It contains a detached completed block, including assembled tool arguments or provider-native final data. Unfinished or invalid blocks produce no completed-block event. Interleaved blocks are observed in completion order; the completed message retains block-index order.
- `ModelMessageEvent` observes the completed middleware output after its iterator has drained and disposed successfully, before `AfterModelCallEvent`. Cached middleware can produce a message event without provider or completed-block events. Before-model denial produces no model-message event. A retried attempt can be observed without being committed to history; an after hook may still change the accepted message.
- `AgentResultEvent` is dispatched once after the final continuation decision and after invocation cleanup. Intermediate resumed cycles do not emit it. Closing a stream at an earlier boundary does not create a final observation or start a hidden continuation.

Model observation callbacks receive the original invocation caller token. `Agent.CancelSignal` remains the separate cooperative signal for explicit cancellation and effective I/O. Existing foreground tool/progress operation tokens and cleanup-hook `None` parameters are retained. Callback failures propagate with the original exception; iterator and after-hook cleanup failures remain secondary. Completing a notification does not itself commit a message or invent a provider acknowledgement.

Input redaction timing and persistence are unchanged. Pinned Python defines `MessageUpdatedEvent` but emits it from bidi message replacement, not ordinary agent redaction. The optional native Bidi package already provides `BidiMessageUpdatedEvent`, with a detached replacement and stable tracking ID, and its session lifecycle already observes those replacements. This increment adds no unsolicited Core redaction callback or unused event alias.

The exact source baseline is `cc167767985c7792c17d8f3ff931243c1611740c`; source comparisons use pinned upstream `3bd98e618320f0f286acbfb2252f72388030421b`. The evidence includes a foreign netstandard custom-hook consumer compiled before these API changes, existing positional constructors, native cancellation/stateful receipt cases, and local Framework architecture checks. This scope does not claim identical whole-agent behavior across SDK languages, hosted-platform execution, or new provider protocol support.
