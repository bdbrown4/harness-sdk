# Binary child-process pipes

Sandbox client stdin and the native Monty worker carry byte protocols. They now share one internal owned-process helper. It uses `System.Diagnostics.Process` for identity, exit notification, waiting and termination. The sandbox's timeout/output/cleanup policy and Monty's framing, worker-ready handshake, host-call cancellation and cleanup remain in their existing callers. This helper is neither a public process API nor a new sandbox boundary.

On modern .NET, the ordinary BCL process launcher selects `new UTF8Encoding(false)` explicitly for redirected stdin. The binary callers use only its raw stream. On the Windows .NET Standard asset, three `AnonymousPipeServerStream` endpoints replace the Framework-created text stdin. Windows receives an explicit three-handle inheritance list; parent endpoints are noninheritable. The child starts suspended, and its managed `Process` lifetime handle and all owned stream endpoints are established before its primary thread resumes. Local copies of child endpoints close on success and on every startup failure. An attachment failure terminates and joins the child, retaining the original exception and secondary cleanup diagnostics. The join has a five-second bound; failure to terminate/reap is reported with the known child PID. Native termination failures are not hidden by an infinite wait.

The existing caller/lifetime token is checked before creation and immediately before releasing the suspended Windows child. Cancellation observed during attachment prevents command execution, reaps the suspended child, and retains the supplied token. Cancellation after release follows the callers' existing termination and drain algorithms. The helper borrows the token and never disposes its source.

The raw stdin holder closes its stream once and performs no text flush. Genuine read/write errors still propagate through each caller's existing error handling. Anonymous pipe flushing has pipe semantics rather than a disk `FlushFileBuffers` operation. No bytes are removed, including a legitimate leading UTF-8 BOM. This does not change the native worker's frame limits or validation.

The causal Framework behavior is visible in Microsoft's [reference implementation of Process.Start](https://github.com/microsoft/referencesource/blob/main/System/services/monitoring/system/diagnosticts/Process.cs): it creates a redirected-input `StreamWriter` with `Console.InputEncoding` and enables `AutoFlush`. A BOM-emitting console encoding therefore sends the preamble during process startup, before a caller's first raw write. Framework lacks the modern per-process `StandardInputEncoding` property. Changing a consumer's console encoding would be global and racy; stripping a leading byte sequence would corrupt valid payloads. The implementation does neither.

This is a shared helper for two existing binary consumers. It composes BCL process and pipe types and confines the necessary legacy startup interop. That follows the readability and composition guidance already referenced in the SDK's design notes and Scott Hanselman's [discussion of unnecessary indirection](https://www.hanselman.com/blog/im-just-a-caveman-the-hanselman-corollary-to-the-clarkewheeler-laws). The reference is design context, not an endorsement.

Tests use a build-only fixture with a private hidden console. They select CP437, UTF-8 with a preamble, or UTF-8 without a preamble; the latter two share code page 65001. They preserve the actual five reported test methods and their byte/frame assertions. Additional contracts cover empty/large/arbitrary/BOM-leading stdin, Unicode and space executable paths/cwd/argv/environment, empty and removed variables, stderr, fast peer exit, parallel EOF, unrelated inherited-handle rejection, attachment failure, repeated startup cleanup, cancellation during attachment, and existing sandbox cancellation/disposal/deadline behavior. Both fixture and test-host pointer sizes are checked, and the host's console encoding/preamble are unchanged. Unix exercises the modern BCL path; Windows-specific handle and console contracts are explicitly conditional.

The original clean 4.8 CI failures and the unchanged-source causal diagnostics remain separate evidence. Local `net48` proof runs on installed Framework 4.8.1, not a claim of clean 4.8 execution. An optional UTF-16 full-test diagnostic was incomplete and stopped; it is not a passing matrix. This change does not modify MCP stdio, native worker assets, jobs, process-tree policies, host configuration, or package native-asset guards.
