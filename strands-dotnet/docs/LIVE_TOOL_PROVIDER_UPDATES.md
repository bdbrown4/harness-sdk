# Opt-in live provider publication

`AgentOptions.EnableToolProviderUpdates` defaults to `false`. When enabled, a provider implementing the optional `IToolProviderUpdates` capability supplies ordered full snapshots through `WatchToolsAsync(context, observer, cancellationToken)`. The existing `IToolProvider` ABI is unchanged. The establishment token is not the lifetime token for the returned subscription.

The provider must deliver an initial snapshot before returning a nonnull owned lease. Until that lease returns successfully, the provider owns provisional subscription cleanup. An Agent tracks each provider declaration before admission, validates its initial batch, and joins failed initialization cleanup. Repeated declarations have independent subscriptions even when they share the same Agent consumer context. Tools and provider instances remain borrowed.

Each declaration can replace only its own registrations. The Agent copies membership and JSON metadata, calls its public tool filter before reading `Spec`, then applies the provider-spec filter to that same captured specification and compiles its input validator. Filters and getters run outside the Agent admission gate. A complete prepared batch either replaces the declaration's table or leaves the previous table intact. Foreign exact/normalized collisions and sharing the same tool reference across different owners are rejected. Refreshed tools append in source order after foreign registrations; model-issued lookup stays exact. This is the TypeScript-style owner-batch replacement behavior, explicitly enabled in native .NET; Python's pinned Agent registry loads provider tools initially only.

Updates accepted during initialization, an invocation, a direct call, abort, explicit classic reduction, or a pending foreground interrupt coalesce to the latest valid batch. Publication occurs when that admission is released. Successful snapshot loading can release a pending foreground interrupt; failed/cancelled snapshot loading cannot publish early. Generation and preparation sequence fences prevent stale work from replacing a newer accepted batch. Terminal `OnError`/`OnCompleted` discards unpublished pending work and retains the last published table. Later notifications from that subscription are ignored.

Publication does not wait for background bodies. A background task admitted from an updating provider captures its original tool reference, detached specification, and compiled input validator in its existing private execution record. Those bindings survive queueing, retry, `InputRequired` resume, and cancellation's terminal status while a physical body still runs. Middleware selecting a different tool retains the existing lookup behavior. The scheduler and cancellation algorithms are unchanged; a terminal task status is not proof that the body exited. Existing shutdown callbacks attempt all handlers and physically stop background work before provider subscriptions and consumers are released.

## MCP composition

`McpToolProvider` implements the optional capability. Agent publication and MCP wire rediscovery are separate opt-ins: configuring the Agent alone delivers the provider's cached initial batch without enabling notifications. Configure the provider's existing `ToolChanges` setting to receive refreshed MCP batches.

One existing MCP watch and RPC pump serves a shared generation. Accepting a versioned complete cache enqueues each consumer's update before invoking the optional application `OnToolsChanged` callback, so a failing application callback does not starve Agent publication. Each subscription has an independent serialized worker and latest-pending snapshot. A blocked consumer does not stall another consumer or the MCP cache worker. Initial delivery is ordered before later queued versions, and the load-to-subscribe handoff captures the latest accepted version under the provider gate.

An establishment failure closes and joins only its provisional observer. A returned lease's disposal suppresses later callbacks and joins its initial and worker activity. Removing one consumer closes and joins all subscriptions for that context while other consumers keep their shared generation. Admission retains the existing idempotent consumer-ID set semantics; repeated declarations have independent leases, and removing that set owner retires all of them. Last-consumer removal joins every outstanding subscription before disposing the owned watch/client. Terminal listen failure is relayed through `OnError`; notification completion uses `OnCompleted`. Refresh or application callback failure does not revert the accepted cache. No automatic reconnect is provided.

Callbacks must cooperate and return. Same-provider lifecycle waits from a live provider callback fail fast, including disposing a subscription or removing a consumer. Expired callback contexts are ordinarily independent after their work completes. During synchronous generation cancellation delivery, an expired captured receipt is conservatively treated as reentrant, preserving the existing bounded cancellation guard. A raw cached Task cannot provide universal self-wait detection. Disposal does not promise to join unrelated work posted by arbitrary application progress callbacks.

The MCP schema-discovery prerequisite retains full-page atomic acceptance, per-call output-validator admission, and each returned tool wrapper's original validator across later discoveries. This live-publication layer does not add a second transport reader or replace those bindings.

## Limits

This capability publishes tables; it cannot freeze arbitrary mutable implementation state inside a borrowed tool or provider. A provider must keep previously handed-out capabilities usable until consumer removal. Harness captured delegation/server catalogs and Bidi provider advertisements have separate lifetimes and are not refreshed by this option. Directory/assembly watching, provider resource unload, automatic reconnect, and those outer catalogs require their own contracts.
