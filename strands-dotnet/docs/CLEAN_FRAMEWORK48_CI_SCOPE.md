# Clean Framework 4.8 CI coverage

The public `dotnet-framework48.yml` candidate runs Compatibility, Monty, Bidi, OpenTelemetry and Cedar in both physical x64 and x86 VSTest hosts. Compatibility/Bidi/OpenTelemetry must execute the shared pointer assertion. Monty must report the pinned real worker handshake, host pointer size and worker pointer bits; Cedar must report its actual bridge process architecture. Their existing dedicated validators remain authoritative. Empty, skipped, failed and mismatched results fail the gate.

The runner reads both `Registry64` and `Registry32` Framework Full keys. Both release values must be in `[528040, 533320)`. It records both views and CLR/OS identity and rejects an installed 4.8.1 runtime. There is no runtime-guard bypass. New or empty evidence directories prevent stale results from satisfying a later invocation.

The workflow stages all five genuine native RIDs and preserves production package/license guards. `native-only` on the reusable Cedar workflow defaults to false. The general Framework workflow requests only its native producer when its caller has not already produced Cedar artifacts. Root CI waits for both native families before supplying the ready flags, so artifact names are not duplicated. A failed/canceled producer cannot admit the Framework job; explicitly skipped producers are valid only when the caller supplies their artifacts, whose downloads remain mandatory.

Monty and Cedar package helpers build independent Framework x64 and x86 consumer outputs. Both run inside the corresponding container invocation with exact native/pointer markers. The separately reviewed Bedrock package helper also supplies independent physical outputs for both architectures. Its three validation files are a supplemental prerequisite; they are absent from frozen source 2f6c6f4. Existing Harness/project, SageMaker, Bidi and OpenTelemetry AnyCPU consumers remain in the x64 invocation; they are not relabeled as x86 executions.

Local evidence comprises two reproduced baseline script defects (three-suite dispatch and a missed second-view4.8.1), an additionally reproduced strict-mode descriptor failure, and 78 passing script/validator contracts in each physical PowerShell5.1 controller. One retained intermediate failure was a null-environment comparison in the test fixture, corrected without a runtime change. The fixture files contain extracted/canonicalized architecture results from the previously recorded installed-runtime matrix. Revalidating these samples is not another native test run. Local parser checks and a real installed4.8.1 rejection supplement the fixtures.

Actual execution of this public Windows Server Core Docker workflow remains pending. The separate GCP Windows/Linux evidence does not certify Docker execution. Complete Monty/Harness release packing still requires the genuine macOS workers; no placeholder native assets or weakened package guard is introduced by this CI coverage change.
