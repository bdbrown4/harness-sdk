# Framework MCP HTTP body cancellation

The native HTTP factories use an owned forwarding `HttpClient` for the netstandard2.0 asset. This fixes an observed .NET Framework response-stream behavior: cancellation of an active `subscriptions/listen` request did not interrupt the physical SSE read. Both local Framework process architectures reproduced the failure; forcing server EOF released the read. Disposing the entire official protocol session first did not release it either.

The forwarding client passes requests to the application-owned `HttpClient`. It keeps the application's headers, authentication handlers, redirects, timeout and other HTTP policy. Its own timeout is infinite. Request method, URI, version, headers, property/options values and streaming content are copied into a forwarding envelope because an `HttpRequestMessage` cannot be sent twice. The envelope never adds disposal of the original request content. Framework's normal outer `HttpClient` automatic content disposal is preserved, as independently characterized without the bridge. The borrowed client and its handler remain application-owned.

The response owns its content and stream. A canceled body read closes only that response stream and physically joins the read. The reported cancellation retains its read token and cause. Existing read/open errors remain primary; later cleanup errors retain their original identities in `Strands.CleanupErrors` without duplicate references. Response/content wrappers are idempotent. The underlying BCL content can itself own a cached stream, so no claim is made that its raw stream receives exactly one `Dispose` call.

Same-client lifecycle waits from a live forwarded handler, body read, cancellation callback or cleanup callback fail promptly. The response-lived receipt expires after physical response cleanup; unrelated clients and later escaped contexts remain usable. During the owned response lifetime the guard is conservative. It does not detect every possible wait on an externally cached task.

The bridge is private and the modern native factory path remains unchanged. It adds no transport reader, RPC pump, session or application callback. Generic `CreateAsync(IClientTransport)` retains application transport authority: a custom transport must supply cooperative cancellation for its own response reads. The bridge closes active reads after body opening; it does not promise to interrupt arbitrary custom `HttpContent.ReadAsStreamAsync` implementations that ignore disposal. If such an open completes after concurrent response disposal, its late stream is closed.

This is a Framework HTTP prerequisite for the separate notification watcher increment, not a claim of automatic reconnect or live Agent tool publication. Local Framework evidence uses 4.8.1 and is not clean 4.8 proof.
