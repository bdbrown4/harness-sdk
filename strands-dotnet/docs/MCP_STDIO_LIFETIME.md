# Convenience stdio process lifetime

The two native `McpClient.CreateStdioAsync` overloads own their launched process and use the official ModelContextProtocol 2.2.0 `StreamClientTransport` for newline-delimited JSON-RPC. There is one official receive pump. Caller-supplied `IClientTransport` implementations retain the separate `McpClientSettings.OwnsTransport` contract; this implementation does not change their process ownership.

On Windows, the SDK starts a `cmd.exe` input gate, assigns it to a kill-on-close Job Object, and only then releases the configured application command. End of input before release cannot start the application command. An exact ASCII acknowledgement is consumed before the official client can send MCP bytes, so CMD cannot consume the first request while reading its release line. This raw read has caller cancellation and a separate one-minute startup deadline; it cannot prefetch application output. The fixed gate expands one private Unicode command value and clears that same environment variable before application execution. CMD AutoRun and delayed expansion are disabled. Cleanup terminates the owned job and observes its active process count reach zero before reporting physical process cleanup complete. This includes descendants that remain after their launcher exits. Job assignment failure rejects the connection without releasing application code. This is process ownership, not OS sandboxing.

Explicit Windows `.exe`/`.com` commands preserve literal percent expressions, embedded quotes and shell operators as argument data. Ordinary CMD command lookup, PATHEXT and application-provided batch wrappers remain available. A batch file can reinterpret its arguments when forwarding `%*`; literal quote arguments therefore fail before launch for batch and extensionless commands. An extensionless executable invocation needing literal quotes must use its actual `.exe`/`.com` path. There is no custom PATH resolver or implicit host lookup to guess whether an extensionless command is a native executable or a batch shim. Windows CR/LF arguments and expanded command lines longer than CMD's 8191-character limit are rejected before process execution. These are explicit native limitations, not a generic Windows argv parity claim.

Modern Unix assets launch the executable with separated arguments and use the platform process-tree termination API while the launcher is alive. A descendant that survives an already-exited launcher may no longer be discoverable through that API. The SDK bounds pipe cleanup and does not promise to reap such an orphan. The `netstandard2.0` implementation rejects Unix process execution before launch; Framework execution uses the Windows job implementation.

The options are copied before connecting. Argument order and empty values, selected environment inheritance, working directory and UTF-8 streams are preserved. The borrowed `StandardErrorLines` callback is isolated from ordinary callback exceptions. An application callback that blocks indefinitely can prevent its own stderr drain from finishing; it cannot turn incomplete cleanup into successful disposal.

`ShutdownTimeout` controls the initial graceful exit wait and the following owned physical cleanup wait. A zero timeout skips the graceful wait and allows five seconds for physical cleanup. Official protocol cleanup also retains its own timeout behavior. If native process or pipe cleanup exceeds its wait, disposal fails with an `IOException` and exposes `Data["Strands.CleanupTask"]` as a `Task<IReadOnlyList<Exception>>`. That task observes late cleanup and never faults. The exception's process-local diagnostic dictionary is separate from Framework exception serialization. Already-completed cleanup failures retain the primary exception and attach distinct secondary failures at `Strands.CleanupErrors`; an exception is never its own secondary failure.

Initialization failure and requested cancellation attempt owned cleanup before returning. The primary initialization error or caller cancellation remains primary if cleanup also fails. The deferred task is then available on the attached cleanup exception. Concurrent disposal calls share the same published task. A successful disposal means the owned cleanup completed; a returned deferred-cleanup diagnostic does not mean it already completed.

The official client's completion details retain the launched wrapper PID, exit code and the last ten stderr lines through `StdioClientCompletionDetails`. A wrapping transport is still reported as an unknown transport kind by task-profile negotiation, as with the existing protocol-observing wrappers; no protocol metadata is fabricated.

The lifetime tests use real managed fixture processes and task-owned directories. They cover launcher exit with a surviving descendant, initialization cancellation, pre-cancellation, UTF-8 and selected environment, CMD/PATHEXT forwarding, and blocked borrowed stderr observers. The deterministic descendant regression is independent of the earlier full-suite directory-in-use failure; that original failure's cause remains unresolved. Windows execution evidence does not establish Unix or clean Framework container compatibility by itself.
