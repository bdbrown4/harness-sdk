# Custom tool batch execution

`AgentOptions.ToolBatchExecutor` optionally supplies a borrowed `IToolBatchExecutor`. Its null default preserves the existing `ToolExecutionStrategy.Concurrent` or `Sequential` implementation and `MaxParallelTools = 8`. A custom executor schedules only the original model-issued batch after common admission and before the existing common result commit. Direct tool calls and physical background bodies retain their existing execution paths.

The SDK provides a `ToolBatchExecutionContext` with detached, read-only `Calls`, the original application-owned `InvocationState`, and `ExecuteAsync(index)`. Each accepted index returns the same task and runs the existing tool pipeline once; retries, hooks, middleware, schema/output validation, telemetry, structured output, background routing and durable human interrupts stay inside that pipeline. The existing supported result-content snapshot is returned, or null when the real call pauses for human input. The executor cannot supply a result, replace an original ID, add calls or write history through this context.

The executor's token and tool pipeline token are linked custom-batch operation tokens. They preserve original hard invocation cancellation and caller token-source ownership; they are not promised to equal the original caller token. The executor is borrowed, may be shared by independent child/Agent instances, and is never disposed by the SDK.

When the executor returns, scheduling admission closes. Previously accepted work is physically joined even when the executor ignored its tasks. Normal return leaves accepted work running; scheduler failure cooperatively cancels its owned linked operation and still joins it. Every late scheduling request is rejected, including a request for an already accepted index, while previously returned tasks remain awaitable. An uncooperative executor or body cannot be forcibly stopped.

After accepted work drains, results are committed in model-issued order. If no human pause exists, unadmitted calls receive SDK error acknowledgements without invented body executions or middleware/telemetry. A human-paused batch keeps unscheduled/unanswered calls incomplete; no skipped acknowledgement replaces pending human input. Completed resume results are retained without replaying remote side effects; the normal structured decoder restoration still occurs.

The first model-issued private pipeline error remains primary. Distinct later pipeline errors, scheduler failure and cleanup errors are retained as secondary causes. Catching or ignoring a scheduled task does not erase the SDK's private pipeline failure. This ordering and SDK-owned result assembly are explicit native choices: pinned Python and TypeScript permit more mutable executor/result internals and differ in sibling failure policy.

A strategy schedules; its own SDK pipeline callbacks must not reschedule that batch. The SDK detects reentry through a propagated live execution context and synchronous pipeline callback prefixes using an expiring async receipt and a bounded synchronous thread receipt. It does not claim universal detection for a later callback that suppresses execution context, an unrelated suppressed Task.Run, or awaiting an already cached self task. This is a cooperative scheduling API, not a security or isolation boundary. No thread receipt spans an await and no application callback runs under the scheduling lock.

This abstraction is influenced by Scott Hanselman's [Please Learn to Think about Abstractions](https://www.hanselman.com/blog/please-learn-to-think-about-abstractions): a thin scheduling capability keeps the underlying execution and cleanup invariants understandable and testable. The reference describes our engineering influence; it is not an endorsement of this SDK or API.

The focused conformance suite covers custom order and default enum paths, shared-task and pipeline accounting, bounded ignored work and physical iterator cleanup, hard caller cancellation, distinct error identities, real pause/resume and fresh structured-decoder restoration, supported JSON/media snapshots, direct tools, delegation, background acknowledgement, late admission, expiring receipts and borrowed child sharing. This optional scheduling feature does not change provider transport behavior or claim live-provider or full-platform validation.
