# Guarded application tool mutation

Agent application registrations can be changed with `AddTool`/`AddTools`, `ReplaceApplicationTool`, `AddOrReplaceApplicationTool`/`AddOrReplaceApplicationTools`, `RemoveApplicationTool` and `ClearApplicationTools`. Replacement retains its insertion slot; new registrations append, including after removal on Framework. A repeated exact name in an add-or-replace batch uses its last value. Missing replacement throws `KeyNotFoundException`; removal returns false when absent.

These APIs control application registrations only. A plugin/provider registration cannot be overwritten, removed or cleared through them. Initialized plugin tools, built-in background management tools and their resource owners remain intact. The current application list is inherited by default children, while plugins initialize independently and invocation-local tools never enter that list. Removing a registration never disposes a borrowed tool or removes a separately transferred `OwnedResources` lifetime obligation.

Changes require an inactive agent: invocation, initialization, direct-tool calls, interrupt abort and classic reduction admissions reject them. A pending interrupt ledger also blocks every mutation, including additions, because its execution bindings must remain stable. Shutdown and disposed agents reject mutations. Reads of an earlier `Tools` snapshot retain their original membership.

Filters run before any candidate `Spec` access. Complete batches prepare schemas and policy checks before publication, then recheck admission and the latest registered state while holding the agent gate. A failed candidate, duplicate or normalized conflict publishes none of that batch. Replacement updates execution schema, tool body, advertisement snapshot and child application inheritance together. Application callbacks run outside the publication lock; their independent completed operations are not rolled back, and an invocation entering during preparation prevents the later commit. Registered custom tools must expose stable specifications, as existing registration requires.

`AgentOptions.ToolNameConflictPolicy` defaults to `ExactOnly`, preserving native behavior. Explicit `RejectNormalized` also rejects case-sensitive hyphen/underscore aliases, as both pinned upstream registries do. This applies to initial and added tools, each plugin/initialization-tool batch, the built-in background manage tool, ephemeral tools and structured-output registration. Validation failures retain existing constructor versus initialization exception families. Failed plugin batches publish none of that batch; earlier successfully initialized sources retain their existing initialization semantics.

`AgentOptions.DirectToolNameResolution` defaults to `Exact`. Explicit `UnderscoreAlias` follows Python direct lookup; `TypeScriptDirect` adds insertion-order lowercase fallback. Exact matches win, alias normalization is one-way, and case fallback does not also rewrite underscores. A successfully resolved public direct request uses the canonical registered name before its before-tool callback and retains the caller's tool-use identifier. Missing direct tools continue to produce the existing native error result. Model-issued and Bidi protocol requests always use exact lookup, even when public direct aliases are enabled.

No mutable standalone registry is exposed from an Agent. TypeScript exposes its complete registry; Python exposes replacement and registry internals. Native application-only authority intentionally leaves generic provider-origin mutation, refresh leases and full provider-aware registry delegation separate. This scope does not add module discovery or hot reload, and does not change tool descriptions, tool ownership, model-issued name normalization, hooks, cancellation or session algorithms.
