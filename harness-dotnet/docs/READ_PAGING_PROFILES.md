# Read paging profiles

`FileTools.CreateRead(files, new ReadConfig { PagingProfile = ... })` selects a text paging contract. The same `ReadConfig` is available through `HarnessOptions.Read`. This adds no tool to the default Harness selection and grants no filesystem authority: reads continue to use the selected sandbox or filesystem.

`NativeIntegral` is the default. Offset and limit accept JSON integer literals or null, with exact integer arithmetic. Missing or null offset starts at line one; missing or null limit selects 2000 lines. Zero and negative offsets clamp the start to the beginning. Limit participates in source-style slice endpoint arithmetic, including zero, negative and very large values. Empty windows retain the original offset diagnostic, using `None` for a missing or null offset. Positive pages keep their prior numbering. There is no separate 10,000-line paging cap.

`Python` is an explicit coercion profile bound to the captured minimum Harness dependency reference: Pydantic 2.5 / pydantic-core 2.14.1 and num-bigint 0.4.4. Integer JSON literals remain exact. Decimal and exponent numbers first become binary64; only finite whole values strictly inside the reference's converted i64 boundaries are accepted. Booleans become zero or one. Strings follow the captured parser's complete branches: a 4300 UTF-8 byte bound, original-length dispatch at 19 bytes, decimal-zero handling before underscore fallback, and the long-integer parser's underscore rules. For example, numeric `1e2` and the string `"2.0"` are accepted; the string `"1e2"` is rejected. The pinned projects allow later dependency minors, so this named reference is not a claim about every unlocked Pydantic version.

The native Python profile advertises `number|string|boolean|null` to make those accepted transport kinds available through ordinary Agent schema validation. Upstream Pydantic advertises an integer/null input schema while applying its coercion internally. The native tool does not bypass or rewrite Core schema validation. Inputs still need to be representable by the native JSON transport; lone-surrogate and non-JSON Python-object behavior is not emulated.

`TypeScript` accepts finite JSON numbers, including fractions, and rejects null, booleans and numeric strings. It uses binary64 values, computes the endpoint sum before truncating each slice endpoint, and preserves the upstream raw fractional numbering and footer labels. Thus offset 2.5 can display labels 2.5 and 3.5. Large integer literals may round as JavaScript numbers do. Missing-offset empty windows display `undefined`. Decimal labels follow the captured ECMAScript shortest representation, including its fixed/scientific thresholds and ties; .NET round-trip formatting is not used as a substitute.

All profiles retain complete lines, existing newline splitting, default 2000-line paging, and the selected reader's existing text-size policy. The built-in `LocalFileSandbox` keeps its 5 MiB default text-read bound; custom readers retain their own policies. Image/document dispatch, media byte limits and model media policy remain separate. Explicit Python/TypeScript inputs are checked before media I/O. Default native media dispatch retains its prior text-paging independence; Agent calls still validate the published schema before invoking any tool.

Cancellation is checked before explicit-profile validation and forwarded to the selected reader. No model, host filesystem fallback, process, interpreter, timer or external numeric engine is introduced. The numeric formatter's conformance vectors include RFC 8785 Appendix B, whose finite IEEE patterns cover subnormals, maximum finite values, decimal thresholds and a rounding midpoint; those are bounded tests rather than a claim of universal JavaScript-engine conformance.
