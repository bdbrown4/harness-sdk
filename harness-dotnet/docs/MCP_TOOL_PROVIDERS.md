# Harness MCP provider declarations

The harness now admits declarative `McpServers` through the native `McpToolProvider` lifecycle. Configuration files and environment references are resolved through the selected sandbox when declarations are created. The resulting arguments, environment, headers, prefixes, filters, authentication and task settings are detached snapshots. Connecting a generation does not reread mutable caller definitions or the configuration file.

`McpServerConfiguration.CreateToolProvidersAsync(sandbox, cancellationToken)` returns an ordered read-only provider list without connecting or discovering tools. An application can supply this list through `AgentOptions.ToolProviders`. Normal `Harness.CreateAsync` appends its configured declarations after the application's core providers, then awaits normal agent initialization. That initialization performs connection/discovery and records accepted provider metadata before constructing the default delegation tool. The provider objects, sandbox, tools, application callbacks and models remain borrowed; the connector-created sessions belong to the provider generation. Final parent/child removal joins physical session cleanup through the existing native client.

Default `McpServers` configuration continues after startup failures unless explicitly made strict. A continued startup failure leaves an empty named declaration. Discovery/schema failures propagate and trigger initialization rollback. This differs from continuing after every MCP failure. The standalone provider's default remains strict. The existing prefix/filter, authentication and negotiated task policies are preserved.

Named application `McpToolProvider` declarations and configured declarations participate in the default `mcp_servers` axis. Names are offered in declaration order; a missing name is warned about and omitted from delegation, and the first duplicate name wins the server axis. Parent tools from later duplicate or nameless MCP providers are not smuggled into the ordinary tools axis. A child's selection removes MCP declarations themselves, retaining only selected original named providers. Other generic provider declarations, including repeated declarations, retain their identities and native per-agent contexts. Server selection cannot restore tools denied by the inherited registration predicate.

The child reconstructs its default delegation binding after its own providers have loaded. It re-offers only its surviving server names to grandchildren and does not retain its parent's controller closure. MCP tool objects and rich/streaming capabilities are shared unchanged; each consumer still has its own captured metadata and lifetime. A parent may close while a child keeps a selected connection alive; excluded connections then close, and the child's final removal closes its remaining generation.

Child admission checks the actual detached provider specification before publishing a batch or notifying initialization observers. A provider cannot rename an already admitted tool object to bypass the parent's frozen name selection: such a change fails initialization and releases that child's consumer. The inherited public tool predicate still runs first, and inherited internal scope constraints compose across descendants. This check uses the same detached specification later advertised by the child, preserving original tool objects and capabilities without rereading mutable metadata after admission. Native generic provider snapshots remain per-agent; application callbacks that read their own mutable tool properties remain application code.

Native API differences are explicit. Already-connected caller-owned `McpClient` instances and `McpRouter` leases are not silently transferred into an owning factory. A supplied named `McpToolProvider` with a fresh-session connector is the typed native declaration form. Bare `McpTool` values remain ordinary borrowed tools. A router remains its existing rich tool/plugin with its own per-agent connection leases and fixed server allowlist; it is not unwrapped into a server provider. Generic refresh, list-changed registry replacement and hot reload are separate capabilities.

Lazy publication changes duplicate-collision timing: a declarative remote tool that conflicts with an application tool is now rejected during provider initialization with the native provider registry's `InvalidOperationException`, after which admitted sessions are released. Application constructor duplicate behavior remains unchanged. The child default delegation tool is also registered in the existing initialization-owned phase after child provider publication; that phase precedes background normalization, interventions and `InitializedEvent`.

## Application identity and startup budget

`McpServerOptions.ApplicationName`, `ApplicationVersion` and `StartupTimeout` are optional. Configuration JSON uses `applicationName`, `applicationVersion` and `startupTimeoutMs`. Omission or explicit null preserves the existing server-name identity, version `1.0.0` and the official native 60-second initialization default. These fields are omitted from default options JSON; a configured timeout is emitted as numeric milliseconds by `McpServerConfiguration`.

An explicit startup budget is positive, no greater than `Int32.MaxValue` milliseconds, and exactly representable as a whole `TimeSpan` tick. JSON accepts exact fractional milliseconds at that resolution and rejects sub-tick or invalid values before connector admission. Identity strings are forwarded without trimming or broad scalar coercion. Direct Core `McpClientOptions` behavior remains authoritative.

The configured budget covers connection/transport setup and protocol initialization using one linked cancellation scope. It is cooperative: an implementation that ignores cancellation is awaited. A late acquired client is disposed before timeout or cancellation settles; caller cancellation and independent failures retain their reviewed cause/cleanup rules. Tool discovery after connection is a separate operation. Caller-owned Core HTTP clients remain borrowed.
